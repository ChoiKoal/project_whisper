## 0. 판정 어휘

| 표기 | 뜻 |
|---|---|
| **REAL** | 실제 출하 코드 경로를 때린다. 실패 = 게임 결함 후보 |
| **DETECTOR** | 일부러 계약 위반을 심은 fixture. **위반을 잡아내면 PASS.** DETECTOR FAIL = 하네스가 눈이 먼 것이고, 위쪽 REAL 결과 전부 무의미 |
| **BLOCKED** | 빌드/모듈/기기 부재로 실행 불가. **FAIL로 표기하지 않는다** |
| **미검증** | 실행했으나 증거가 부족해 판정 보류 |

정적 검사·데스크톱 시뮬레이션 결과를 실기기 PASS로 쓰지 않는다.

## 1. 🔴 AC A 반례 — 소스에서 확인된 중복 지급 경로

수집 명세 A는 "연타 / 동시클릭+touch / **queue_free 전 재호출**"을 명시한다.
스냅샷 소스를 읽은 결과 **세 번째 벡터가 현재 코드에서 열려 있다.**

### 근거 (인용)

`gatherable.gd`:
```gdscript
func can_gather() -> bool:
    return item_id != "" and not (unique and _spent)

func gather() -> String:
    if not can_gather(): return ""
    Inventory.add(granted, amount)
    GameState.item_gathered.emit(granted)
    if unique: _spent = true
    else:      queue_free()
```

- **비-unique 객체에는 `_spent` 가드가 없다.** `unique and _spent`가 항상 false라
  `can_gather()`는 사실상 `item_id != ""`뿐이다.
- 중복 방지를 **`queue_free()` 하나에만** 의존하는데, Godot의 `queue_free()`는
  프레임 종료 시 반영된다. 즉 **같은 프레임 내 두 번째 호출은 가드를 그대로 통과**한다.

호출부 두 곳 모두 `is_queued_for_deletion()`을 보지 않는다:
```gdscript
# interaction_controller.gd:538  (facing/E 경로)
if act_object != null and act_object.has_method("can_gather") and act_object.can_gather():
    var granted: String = act_object.gather()

# interaction_controller.gd:565  (interact_with_object — 터치 도착 경로)
if obj.has_method("can_gather") and obj.can_gather():
    var granted: String = obj.gather()
```

참고로 `touch_controller.gd`는 **경로/차단 판정에서는** `is_queued_for_deletion()`을
검사한다(97, 146행). 즉 이 가드의 필요성은 코드베이스가 이미 알고 있고, **채집 지급
경로에만 빠져 있다.**

### 가설의 한계 (정직하게)

- 나는 **실행하지 않았다.** 두 경로가 실제로 한 프레임에 겹치는지는 입력 처리
  순서에 달려 있고, 그건 빌드에서 확인해야 한다.
- 따라서 이건 **"확정 결함"이 아니라 "소스상 열려 있는 경로 + 최우선 재현 대상"**이다.
- 카나 쪽 순수 모듈이 커밋 가드를 갖는다면, 통합 시 이 구멍이 덮일 수도 있다.

### 재현 절차 (빌드 수령 즉시 1순위)

1. 새 게임, 비-unique 채집물(꽃/작은 돌) 하나 앞에 선다
2. **PC**: E를 1프레임 간격으로 연타 / **또는** E 누른 프레임에 같은 대상 클릭
3. **모바일**: 대상 탭으로 이동 → 도착 프레임에 한 번 더 탭
4. 인벤토리 증가량과 `item_gathered` 발생 횟수를 센다

| | 기대 | 실패 신호 |
|---|---|---|
| 인벤토리 | +amount **1회** | +2×amount |
| `item_gathered` | 1회 | 2회 (퀘스트/도감 이중 카운트 위험) |
| 노드 | 1회만 제거 | — |

**로그/캡처**: `item_gathered` 타임스탬프 로그, 인벤토리 전/후, 입력 프레임 기록,
화면 녹화(+1 피드백이 두 번 뜨는지).

**심각도 초안**: major. 재화 인플레보다 **퀘스트·도감 신호 이중 발생**이 더 위험.

### 처방 방향 (구현은 루비/카나 몫)

`can_gather()`에 `and not is_queued_for_deletion()` 추가, 또는 비-unique에도
`_spent` 래치를 적용. **호출부마다 가드를 다는 방식은 비추천** — 진입점이 둘이고
앞으로 늘 수 있어서, 가드는 `Gatherable` 안에 한 번만 두는 게 맞다.

## 2. AC별 테스트 명세

### A. 1행동 = 1지급
| # | 입력 | 기대 | 실패 신호 | 플랫폼 |
|---|---|---|---|---|
| A1 | 같은 프레임 `gather()` 2회 | +1, signal 1 | +2 / signal 2 | 하네스 |
| A2 | `interact_with_object` **동일 진입점** 2회 | +1 | +2 | 하네스 |
| A3 | unique 대상 2회 | +1, 노드 잔존 | +2 또는 소멸 | 공통 |
| A2b | E키 경로 + 터치 도착 경로 동일 프레임 | +1 | +2 | **BLOCKED** (컨트롤러+입력 주입 필요) |
| A4 | **DETECTOR** 의도적 2회 add | 2/2 잡아냄 → PASS | 1이면 하네스 불량 | 하네스 |
| A5-plain | **`Inventory.item_added`** 리스너에서 같은 대상 `gather()` 재호출 (budget 1) | 신호 1회 | 신호 2회 | 하네스 |
| A5-unique | 위와 동일, unique 대상 | 신호 1회 | 신호 2회 (**인벤 증감으론 안 보임**) | 하네스 |

> **A5 근거** (루비 지적 반영, 정본 소스 확인):
> `Inventory.add()` 자체가 `item_added` / `changed`를 **동기 emit**하고 `gather()`로
> 돌아온다. 즉 재진입 창은 `item_gathered`보다 **더 앞**에 열린다.
> ```gdscript
> _stacks[id] = current + to_add
> item_added.emit(id, to_add)   # ← 여기서 이미 재진입 가능
> changed.emit()
> ```
> 따라서 가드는 `item_gathered` 앞이 아니라 **`Inventory.add()` 진입 전**이어야 한다.
> 확정 순서: **노드 가드 → Inventory.add → 기타 emit → queue_free 예약**.
>
> **unique는 개수로 탐지 불가**: `add()`가 `to_add = clampi(1 - current, 0, amount)`로
> 상한을 걸어 두 번째 지급이 0이 된다. 그래서 A5·A3는 **신호 횟수**로 판정하고,
> 인벤토리 증감은 보조 지표로만 쓴다. 재진입은 budget 1회로 제한해 무한 재귀를 막는다.

### B. commit 경계
| # | 입력 | 기대 | 실패 신호 |
|---|---|---|---|
| B1 | commit 전 취소 | 지급 0 | 지급 발생 |
| B2 | commit 직후 대상 파괴 | 정확히 1 | 0(유실) 또는 2(재지급) |
| B3 | commit 직후 씬 전환·세이브 | 1, 세이브에 반영 | 로드 시 유실/중복 |
| B4 | 연출 실패(에셋 누락) | 지급 유지 | 롤백 또는 재지급 |

> B4가 중요하다. 명세가 "연출 실패는 지급을 롤백/재지급하지 않음"을 못 박았고,
> 이건 **연출과 상태를 분리했는지** 보는 축이다.

### C. 취소·복구
거리 이탈 / 대화 잠금 / 대상 소멸 / 앱 비활성 각각에서 **입력 복구**를 확인.
타 owner의 lock을 강제로 풀지 않는지도 관찰(권한 침범은 그 자체가 결함).

### D. 바위 통행
채집 전 4방향 차단 → 클릭 우회 → 채집 후 통과 → respawn 후 재차단.
**이동 중 respawn**이 제일 위험: 경로 재계획 또는 안전 취소 중 하나여야 하고,
캐릭터가 지형에 박히면 blocker.

### E. 재질 구분
자막을 가린 채 녹화 → 꽃/돌/나무를 **동작·반응·소리만으로** 구분할 수 있는가.
획득량 표시 정확성 별도 확인. *효과 강도로 원화를 가리는 것은 PASS가 아니다.*

### F. 터치 전용 루프
채집→Fusion→배치/취소→대화 닫기→귀환을 **터치만으로**. 가로/세로 모두.
- 대화 닫는 탭이 뒤 오브젝트 채집으로 **새는지**(drop-through)
- hitbox 크기, 안전영역 잘림
- **데스크톱 시뮬은 실기기 증거와 분리 기재**

### G. 연속 플레이 (재미 검수)
주입 없이 새 게임 완주. 아래를 **관찰 기록**으로 남긴다.

| 항목 | 기록 방식 |
|---|---|
| 최초 채집이 읽히나 | 무엇을 보고 알았는지 |
| 최초 조합/발견이 다르게 느껴지나 | 채집과 구분되는 지점 |
| 최초 월드 변화가 보이나 | 내가 바꾼 걸 알아채는 순간 |
| 다음 할 일이 보이나 | 막힌 지점·시각 |
| 반복 피로 | 같은 동작 N회째부터 지루한지 |
| 기다림 | 대기 구간 길이 |
| 조작 오해 | 의도와 다르게 동작한 입력 |
| 같은 재질 피드백 | 다른 대상인데 같게 느껴진 쌍 |

**"도파민 PASS" 같은 문구는 쓰지 않는다.** 지루했던 구간은 초 단위로 적고 대안을 제안.

## 3. 카나 순수 모듈 API 반례 (모듈 수령 전 사전 설계)

모듈이 아직 없어 **계약 기준 반례**만 준비. API 확정되면 케이스화한다.

1. `begin` 두 번 연속 → 두 번째는 무시 또는 명시적 거부여야. 상태 덮어쓰기면 취소가 미아가 됨
2. `commit` 두 번 → 두 번째 지급 0
3. `cancel` → `commit` 순서 → 지급 0
4. `commit` → `cancel` 순서 → **롤백 없음** (B4와 같은 원칙)
5. 대상 교체 후 `commit` → 원래 대상의 아이템이 나오면 안 됨
6. `begin` 후 프레임 재진입 → 중복 진행 금지
7. 모바일 mouse 에뮬레이션: 한 번의 탭이 touch + emulated click **두 이벤트**로 들어올 때 1회만
8. 모듈이 시간(타이머)에 의존한다면 **프레임 드랍 시** 조기/중복 commit 여부

## 4. 산출물 / 경계

- `harvest_acceptance_harness.gd` — **후보 파일, setup 미검증**. 실행 기록 없음

## 5. 루비에게 필요한 것 (blocked 해소 조건)

1. **동결 빌드 또는 소스 ZIP + hash + 실행 명령** (현재 팩은 부분 소스라 실행 불가)
2. **격리 세이브** (v1 / v2 각각). 실사용 세이브는 쓰지 않는다
3. `InteractionController`를 하네스에서 인스턴스화하는 방법 (A2가 여기 막혀 있음)
4. 카나 순수 모듈 API (B1·§3 전체가 여기 막혀 있음)
5. 실기기 접근 가능 여부 — 불가하면 **AC F는 데스크톱 시뮬까지만** 하고 실기기는 미검증으로 남긴다
